## 一、项目定位与愿景

**Smart Prompt** 是一个面向 AI/Agent 工具用户的"输入框旁提示词协作助手"。核心用户故事：

1. 用户在 ChatGPT/Claude/Codex 等工具输入框打字时，小人入口自动出现
2. 点击后智能判断输入状态（空/半成品/完整），生成合适的 prompt
3. 一键填入输入框，不自动发送
4. 同时推荐相关的 skill/rules

**一句话定位**：输入框旁的 Prompt Copilot，把模糊想法、半成品提示词和完整输入自动转成适合当前 AI 工具的高质量 prompt。

## 四、发现的问题与偏差

### 🔴 严重问题

#### 1. 目标工具 safe candidate 判定过严，桌面端可用性受限

**问题**：Codex 等工具的 composer 区域被标记为 `browser_like_composer_blocked`，`safeCandidateCount=0`。虽然这是安全设计，但导致：
- 桌面端小人在大多数真实工具中只能显示 visual-only 锚点，不能触发 Fill
- 用户看到小人但无法一键填入，体验断裂
- 唯一通过的 Fill 是 Codex 的 clipboard fallback 路径

**偏差**：PRD 说"桌面：accessibility set value；失败时剪贴板粘贴兜底"，但实际 safe candidate 判定过于保守，clipboard fallback 几乎不可用。

#### 2. prompt-quality.js 过度膨胀（173KB / 3523 行）

**问题**：单个文件包含：
- 质量评分逻辑
- 反馈闭环系统
- 策略实验分配
- 策略权重政策
- 质量提升报告
- 失败原因策略
- 自我改进反思
- 进化候选报告
- 实验结果报告
- 任务结果报告

这远远超出了"prompt 质量评分"的职责边界。

**影响**：
- 维护困难，每次修改都要理解整个反馈闭环
- buildPrompt() 函数被 13 个 `context?.xxxGuidance` 参数膨胀
- buildLlmMessages() 的 system prompt 塞入了大量聚合指标说明
- 下游 LLM 收到的 prompt 过长，浪费 token

#### 3. 缺少用户反馈采集机制

**问题**：PRD 定义了完善的指标体系（Insert 成功率、保存率、Undo/Retry），但：
- 浏览器扩展有反馈事件框架，但实际采集深度不够
- 桌面端没有用户反馈 UI（满意/不满意/编辑后使用）
- `prompt-quality.js` 的反馈闭环是"系统自学习"，不是"用户直接反馈"
- 真实内测数据尚未收集（PRD M5 阶段标记"真实用户数据待收集"）

**偏差**：PRD 第 13 节定义了 6 项成功指标，但产品没有对应的用户反馈入口。

#### 4. 版本管理混乱

**问题**：
- 只有一个 git tag：`v0.2.0-beta.1`
- 但代码经历了 V2 → V3 → V4 → V5 → V6 多次迭代
- 没有 CHANGELOG，没有 release notes 的持续维护
- `agent_memory/` 中有大量归档的进度/上下文/bug 文件（共 238KB）
- `.runtime/` 目录有 4282 个文件，`.omx/` 有 187 个文件 — 这些都是开发过程产物，不应该在仓库中

### 🟡 中等问题

#### 5. Local Service 代码重复与耦合

**问题**：`server.js` (1028 行) 中：
- `sanitizeDesktopFillEvidence()` 和 `sanitizeDesktopPromptState()` 做了大量隐私脱敏，但脱敏逻辑分散
- `applyExperimentGuidance()` 将 prompt-quality 的实验逻辑直接嵌入 HTTP handler
- `/generate` 端点同时处理 LLM 调用、skill 推荐、质量评分、实验分配 — 职责过多

#### 6. Browser Extension 的本地服务桥接脆弱

**问题**：
- 扩展通过 `http://127.0.0.1:17371` 连接本地服务
- 如果用户没有安装桌面壳，本地服务可能不运行
- 虽然有 template fallback，但 fallback 生成的 prompt 质量远低于 LLM
- 扩展的 `local-service-client.js` 只有 3KB，错误处理和重试逻辑薄弱

#### 7. Site Adapters 的 Selector 维护成本高

**问题**：`smart-prompt-core.js` 中 `SITE_ADAPTERS` 硬编码了 12 个站点的 CSS selector 列表：
- Replit 有 14 个 selector
- Doubao 有 16 个 selector
- 站点改版时需要手动更新
- 没有自动化测试来验证 selector 是否仍然有效

**偏差**：PRD 说"失败站点原因：至少记录 selector 未命中"，但没有看到 selector 健康度监控系统。

#### 8. 缺少端到端集成测试

**问题**：
- 浏览器扩展有单元测试 (`npm test`)
- 桌面壳有交互测试 (`desktop-shell-interaction.test.js`)
- 本地服务有单元测试
- 但**没有任何跨组件的集成测试**：扩展 → 本地服务 → LLM Gateway → 填入 的完整链路没有自动化测试

#### 9. 文档与代码不一致

**问题**：
- README.md 说"默认不读取或上传整页文本"，但 `prompt-quality.js` 的策略系统隐含了"读取和分析用户历史 prompt"的逻辑
- PRD 说"第三方 skills 默认不可执行脚本"，但 skill import 的代码 (`skill-library.js` 仅 1.7KB) 对 imported skill 的风险标记过于简单
- PRD 定义了 `PilotMetric` 数据结构，但 store.js 中的实际存储结构与 PRD 定义不完全匹配

---

### 🟢 轻微问题

#### 10. Rust 编译产物污染仓库

**问题**：`apps/desktop-shell/src-tauri/target-*` 目录下有多个编译 target 目录（`target-p25-xxx`），累计包含大量自动生成代码。虽然 `.gitignore` 忽略了大部分，但仍有编译中间产物占用空间。

#### 11. 脚本命名混乱

**问题**：`scripts/` 下有 52 个脚本，命名风格不统一：
- `check-v2-*.ps1` / `check-v3-*.js` / `check-v4-*.ps1` — 版本号前缀
- `check-p24-*.ps1` / `check-p25-*.ps1` — 特性编号前缀
- `critic-*.ps1` — 验收脚本
- 同一个功能可能有多个版本的脚本（v2/v3/v4/v5/v6）

#### 12. 缺少错误监控和远程诊断

**问题**：
- 本地服务有 `/diagnostics/export` 端点
- 但用户无法主动触发诊断（没有 UI 入口）
- 没有远程错误上报机制
- 用户遇到问题只能手动查看日志

## 五、优化方案

### 优先级 P0：立即可做

#### 优化 1：拆分 prompt-quality.js

**目标**：将 3523 行的单文件拆分为多个职责清晰的模块。

**方案**：
```
packages/shared/
├── prompt-quality/
│   ├── scorer.js          # scorePromptQuality() — 质量评分
│   ├── structured-output.js # parseStructuredLlmResponse()
│   ├── feedback.js        # buildFeedbackProfile(), buildFeedbackSummary()
│   ├── strategy.js        # buildPromptStrategyPlan(), buildStrategyInsights()
│   ├── quality-lift.js    # buildPromptQualityLiftReport()
│   ├── failure-reasons.js # buildFailureReasonReport(), buildFailureReasonPolicy()
│   └── experiments.js     # buildExperimentAssignment(), buildExperimentOutcomeReport()
└── prompt-quality.js      # 向后兼容的 barrel export
```

**收益**：
- 每个文件 < 500 行，易于维护
- buildPrompt() 不再被 13 个 guidance 参数膨胀
- LLM system prompt 只包含必要的策略摘要（< 500 字）

#### 优化 2：建立用户反馈 UI

**目标**：让用户能对生成的 prompt 进行直接评价。

**方案**：
1. Prompt Card 底部增加 👍/👎 按钮
2. 点击 👎 后弹出原因选项：
   - "太长" / "太短" / "不相关" / "格式不对" / "其他"
3. 反馈数据存入本地 store，关联到对应的 mode/tool/site
4. 定期（每周）将反馈聚合到 `feedbackSummary` 中，用于下一轮生成

**实现**：
- 浏览器扩展：在 prompt card DOM 中添加反馈按钮
- 桌面壳：在 overlay expanded 卡片中添加反馈按钮
- 本地服务：`POST /feedback` 端点接收反馈

#### 优化 3：改善桌面端 safe candidate 判定

**目标**：在保持安全的前提下，让更多工具可以使用 Fill 功能。

**方案**：
1. 将 `browser_like_composer_blocked` 分类细化：
   - 对于已验证安全的工具（Codex 已通过），自动提升到 `safeCandidate`
   - 对于未验证的工具，保持 `browser_like_composer_blocked`
2. 增加"受信任工具白名单"配置，允许用户标记常用工具为可信
3. 对可信工具，跳过严格的 safe candidate 检查，直接使用 UIA value pattern 写入

**实现**：
- `desktop-tool-profiles.js` 增加 `trustedTools: ['codex', 'claude-code', ...]`
- `desktop-input-detector.js` 对可信工具放宽 safe candidate 判定
- 所有写入仍经过 foreground + no-auto-submit 守卫

### 优先级 P1：短期改进

#### 优化 4：引入自动化 Selector 测试

**目标**：减少站点改版导致的 Insert 失败。

**方案**：
1. 为每个站点适配器编写 headless 浏览器测试
2. 使用 Puppeteer/Playwright 加载站点，查找输入框
3. 验证 selector 是否命中，记录命中率
4. 每周自动运行，失败时告警

**实现**：
```javascript
// tests/site-adapters/live.test.js
describe('ChatGPT adapter', () => {
  it('should find input textarea', async () => {
    const adapter = SITE_ADAPTERS.find(a => a.id === 'chatgpt');
    const elements = await page.$$(adapter.inputSelectors.join(','));
    expect(elements.length).toBeGreaterThan(0);
  });
});
```

#### 优化 5：建立端到端集成测试

**目标**：验证 扩展 → 本地服务 → LLM → 填入 的完整链路。

**方案**：
1. 使用 mock LLM server（返回固定 prompt）
2. 模拟扩展调用 `/generate`，验证返回格式
3. 模拟桌面 shell 调用 `/desktop/fill`，验证写入逻辑
4. 覆盖正常路径和所有失败路径

#### 优化 6：改进脚本管理

**目标**：清理 52 个脚本的混乱局面。

**方案**：
1. 删除已过时的 v2/v3/v4 脚本（保留 critic-v2.ps1 作为基准）
2. 统一命名：`verify-<feature>.js`（所有脚本使用 `.js` + Node）
3. 创建 `scripts/verify-all.js` 作为总入口，按优先级运行各验证
4. 将版本相关的报告移到 `research/verified/<version>/` 目录

#### 优化 7：建立文档体系

**目标**：让新贡献者能在 30 分钟内理解项目。

**方案**：
1. 重写 README.md，简化为：快速开始 + 架构概览 + 开发指南
2. 创建 `CONTRIBUTING.md`：如何添加新站点、如何添加新 provider
3. 创建 `ARCHITECTURE.md`：详细架构图 + 数据流 + 关键设计决策
4. 将 PRD 拆分为：
   - `docs/product/` — 产品文档（PRD、竞品分析、用户故事）
   - `docs/engineering/` — 技术文档（架构、API、部署）
   - `docs/research/` — 研究记录（验证报告、实验结果）

### 优先级 P2：中期规划

#### 优化 8：Skill 推荐升级

**目标**：从 keyword matching 升级到 embedding-based matching。

**方案**：
1. 使用轻量级本地 embedding（如 `transformers.js` 或 `onnxruntime-web`）
2. 为每个 skill 生成 embedding 向量
3. 用户输入时计算语义相似度，而非 keyword 重叠
4. 保留 keyword 作为 fallback

#### 优化 9：远程诊断与错误上报

**目标**：让用户能一键诊断问题，开发者能看到聚合错误。

**方案**：
1. 桌面壳设置页增加"诊断报告"按钮
2. 生成本地诊断包（provider 状态、sidecar 健康、端口、最近错误）
3. 用户可选择上传到远程（匿名，不含 prompt 内容）
4. 开发者后台聚合错误，发现高频问题

#### 优化 10：清理仓库结构

**目标**：减少仓库噪音，提高可维护性。

**方案**：
1. 将 `.runtime/` 和 `.omx/` 移出仓库（加入 `.gitignore`）
2. 将 `agent_memory/archive/` 归档到外部存储
3. 清理 `target-p25-*` 编译产物
4. 创建 `.gitattributes` 统一行尾处理

## 六、总结

### 项目健康度评估

| 维度 | 评分 | 说明 |
|------|------|------|
| 架构设计 | ⭐⭐⭐⭐ | 三层分离清晰，隐私边界明确 |
| 代码质量 | ⭐⭐⭐ | 核心逻辑清晰，但 prompt-quality.js 过度膨胀 |
| 测试覆盖 | ⭐⭐ | 单元测试齐全，但缺少集成测试和自动化 selector 测试 |
| 文档完整性 | ⭐⭐⭐ | PRD 详细，但缺少架构文档和贡献指南 |
| 版本管理 | ⭐⭐ | 只有一个 tag，迭代历史混乱 |
| 用户体验 | ⭐⭐⭐ | 浏览器端体验完整，桌面端 Fill 受限 |
| 安全性 | ⭐⭐⭐⭐⭐ | 隐私边界设计优秀，凭证保险箱完善 |

### 核心建议

1. **立即**：拆分 `prompt-quality.js`，减少单文件复杂度
2. **本周**：建立用户反馈 UI（👍/👎），收集真实使用数据
3. **本月**：改善桌面端 safe candidate 判定，让更多工具可用
4. **本季度**：完成真实内测闭环，验证核心价值主张

### 项目价值判断

Smart Prompt 的定位非常有价值 — "输入框旁的 Prompt Copilot" 填补了 prompt library 和 OS-level copilot 之间的空白。核心差异化（环境识别 + 三模式判断 + 一键填入 + skill 推荐）在当前市场上没有直接竞品。

当前最大的风险不是技术，而是**缺乏真实用户数据**。建议尽快启动小规模内测，验证：
- 用户是否真的觉得"比自己写更快"
- 三模式判断的准确率
- 哪个站点的 Insert 失败率最高
- skill 推荐的采纳率
